# 리뷰 대상: 자격증 카탈로그(certification_catalog) 스키마 리팩터링 계획

- 배경: 회원마다 `certification.id`가 다르게 발급되는데, 문제은행(`certification_question`, `subject`)은 고정된 id 하나에만 연결돼 있어 특정 회원만 문제를 풀 수 있는 버그가 있었음.
- 채택된 방향: (b) 권장안 — `certification_catalog` 마스터 테이블을 신설하고, 회원 개인 기록/문제은행이 모두 이 마스터 id를 참조하도록 전환.
- 이 문서는 12개 역할 스킬(`.claude/skills/review-*`)로 위 계획을 각각의 관점에서 검토한 결과다. 실제 코드 구현 전 단계이며, 아래 조건부 승인 항목을 반영한 뒤 구현에 들어가는 것을 전제로 한다.

---

## 1. 백엔드 (review-be)

**판정: 조건부 승인**

- `CertificationCatalogService.getOrCreateByName`의 동시성 처리(unique 제약 위반 시 재조회)가 계획에 명시돼 있는 점은 적절함. 단, `@Transactional` 격리 수준까지는 명시 안 됨 — MySQL/MariaDB 기본 REPEATABLE READ에서도 unique 제약 위반 예외 기반 재조회 패턴은 안전하므로 별도 조치 불요.
- `CertificationQuizController`의 경로 변수를 `{certificationId}` → `{catalogId}`로 바꾸는 리네이밍 범위가 큼. 컴파일 에러로 누락은 잡히지만, **템플릿(Thymeleaf)의 `${certificationId}` 참조는 컴파일 타임에 안 잡히고 런타임에야 드러남** — 리네이밍 후 반드시 각 화면을 직접 열어 확인해야 함.
- 예외 처리 방침에 "찾거나 만들기 실패 시 사용자에게 보여줄 메시지"가 빠져있음 — `IllegalStateException` 등으로 던지고 끝낼지, 자격증 등록 자체를 실패 처리할지 명시 필요.

**리스크**: 템플릿 참조 누락은 배포 후에야 발견될 가능성이 큼 (컴파일러가 못 잡음).

## 2. 프론트엔드 (review-fe)

**판정: 조건부 승인**

- 영향받는 템플릿 5종(quiz-list, subject-list, quiz, quiz-empty, quiz-complete) + 관리자 3종이 계획에 다 나열돼 있음 — 누락 없음.
- `quiz-list.html`에서 링크가 `cert.id` → `cert.catalogId`로 바뀌는데, **`catalogId`가 null인 개인 기록(과거 데이터 중 매칭 실패분)이 있으면 링크가 깨짐**. 계획에 "catalogId nullable 가능"이라고 가정돼 있는데, 화면에서 null인 경우 어떻게 보여줄지(문제풀이 버튼 비활성화 등) 명시가 빠져 있음.
- 관리자 드롭다운을 "#id 회원명" → "자격증명"으로 바꾸는 건 UX 개선이지만, 동명이인처럼 같은 이름의 자격증이 실수로 두 개 생기는 경우를 관리자가 구분 못 하게 됨 — id는 그대로 괄호로 같이 보여주는 걸 권장.

**리스크**: catalogId가 null인 개인 기록에 대한 화면 처리가 계획에 없음 → 최소 하나는 반드시 결정 필요.

## 3. 기획/PM (review-pm)

**판정: 승인**

- 해결하는 문제가 명확함(다른 회원은 문제를 아예 못 품) — 실사용자 임팩트가 크므로 지금 우선순위로 타당.
- 범위가 "문제 해결에 필요한 만큼"으로 잘 절제됨. catalog 관리 CRUD 화면을 별도로 만들지 않기로 한 결정(인계문 7번)은 과잉설계를 피한 좋은 판단.
- 포트폴리오 관점에서도 "스키마 설계 결함을 발견하고 근본 원인을 분석해 구조적으로 해결"은 面接에서 이야기하기 좋은 소재.

**리스크**: 없음(이 역할 관점에서는 추가 리스크 없음).

## 4. 보안 (review-security)

**판정: 승인**

- 새로 추가되는 쿼리들도 기존 컨벤션대로 `#{}` 파라미터 바인딩을 유지하는 계획 — SQL 인젝션 신규 위험 없음.
- 관리자 문제 관리 화면의 드롭다운 소스를 "전체 회원의 개인 기록"에서 "카탈로그 목록"으로 바꾸는 것은 **부수적으로 보안도 개선**됨 — 기존엔 관리자 화면에 다른 회원의 개인 정보(회원 식별자)가 노출되고 있었는데, 그게 사라짐.
- 다만 `CertificationQuizController` 상단 주석에 이미 기록된 기존 취약점(`memberId`를 세션이 아니라 URL 파라미터로 신뢰하는 문제, IDOR 가능성)은 이번 작업 범위 밖으로 남겨두는 게 계획에 명시돼 있음 — **범위 제외는 타당하나, 이번에 경로가 어차피 많이 바뀌므로 별도 후속 작업 티켓으로라도 남겨야 함**.

**리스크**: 기존 IDOR 취약점이 이번 리팩터링과 무관하게 계속 남음 — 후속 조치 필요(이번 계획의 결함은 아님).

**리스크**: 없음.

## 6. 장애분석가/SRE (review-incident)

**판정: 조건부 승인**

- 이 프로젝트가 최근 "마이그레이션 누락으로 인한 500 장애"를 겪었던 점을 고려하면, 이번에도 **V12 마이그레이션이 로컬에서 100% 검증되기 전엔 절대 push하면 안 됨** — 계획의 인계문 6번("로컬에서 직접 확인하기 전엔 완료로 보지 말 것")이 이 원칙을 담고 있어 적절함.
- 백필 검증 쿼리(고아 데이터 개수 SELECT)가 계획에 언급은 됐지만, **구체적인 쿼리문 자체는 아직 없음** — 실제 구현 단계에서 반드시 작성해서 마이그레이션 파일 주석에 남겨야 함(기존 006~008 마이그레이션의 "검증용 쿼리" 컨벤션을 그대로 따를 것).
- 배포 후 확인 신호("Successfully applied 1 migration to schema")는 이미 이전 장애 대응으로 익힌 절차이므로 그대로 재사용 가능.

**리스크**: 백필 매칭(이름 문자열 비교)이 로컬/운영 DB 간 데이터가 다르면 각 환경에서 다른 결과가 나올 수 있음 — 로컬에서 검증됐다고 운영에서도 100% 같은 결과라는 보장은 없음. 운영 배포 직후에도 검증 쿼리를 반드시 한 번 더 실행할 것.

## 7. 테스트/QA (review-test)

**판정: 조건부 승인**

- "서로 다른 두 회원이 같은 이름으로 등록 → 둘 다 문제풀이 가능" 시나리오가 명시된 건 핵심을 정확히 짚음.
- 다만 **동시성 테스트**(두 회원이 정확히 같은 순간에 같은 이름으로 처음 등록 — `getOrCreateByName` 레이스 컨디션)는 계획에 로직만 있고 테스트 케이스로는 없음. 자동화가 어렵다면 최소한 코드 리뷰 시 수동으로 로직을 검증하는 체크포인트로 남겨야 함.
- 이름에 공백/오타가 있는 케이스(예: "피부자격증" vs "피부 자격증")에 대한 테스트가 없음 — 백필 실패 가능성이 가장 큰 지점인데 검증 시나리오가 없는 건 공백.

**리스크**: 이름 매칭 실패 케이스에 대한 테스트 부재.

## 8. 아키텍처 설계 (review-architecture)

**판정: 조건부 승인 — FK 설계 재검토 권고**

- 방향 자체(마스터 테이블 분리)는 옳음 — "id가 우연히 맞아야 동작하는" 현재 구조는 명백한 설계 결함이고, 이걸 구조적으로 없애는 게 맞는 접근.
- **사용자가 지적한 "FK 남발" 우려에 동의하는 지점이 있음**: 계획대로면 `certification.catalog_id`, `subject.catalog_id`, `certification_question.catalog_id` 세 곳에 모두 새 FK가 생김. 이 중:
  - `subject.catalog_id`, `certification_question.catalog_id` → **필수**. 문제은행이 회원과 무관하게 카탈로그에 고정돼야 하는 이번 버그의 핵심 해결책이므로 FK로 강하게 묶는 게 맞음.
  - `certification.catalog_id` → **재검토 권고**. 이건 회원 개인의 자유 텍스트 기록과 카탈로그를 "느슨하게" 연결하는 용도라, 엄격한 FK(참조 무결성 강제)보다는 **nullable 인덱스 컬럼 + `ON DELETE SET NULL`** 정도로 완화하는 걸 권장. 개인 기록은 카탈로그가 나중에 정리/병합돼도 깨지면 안 되는 성격이라, 강한 FK 제약이 오히려 유연성을 해칠 수 있음.
- 네이밍(`certificationId` → `catalogId`)을 전면 리네이밍하기로 한 결정은 "이름과 의미의 불일치가 이번 버그의 근본 원인이었다"는 진단과 정확히 일치 — 지지함.

**리스크**: FK 3개를 다 강한 제약으로 만들면, 나중에 카탈로그 데이터를 정리(중복 병합 등)할 때 세 테이블 모두 잠금/영향을 받아 운영 부담이 커짐.

**판정: 승인**

- 계획 문서 자체가 배경(왜)·대안 비교·트레이드오프를 잘 담고 있어 나중에 봐도 이해 가능한 수준.
- 마이그레이션 파일에 목적/롤백을 주석으로 남기는 기존 컨벤션이 계획에도 유지됨.
- 권고: 구현 완료 후 `docs/PROJECT_OVERVIEW.md` 또는 `docs/logical_data_model.md`(이미 존재)에 `certification_catalog` 테이블과 관계를 반영해야 함 — 계획의 "변경 대상 파일"에는 빠져 있으므로 구현 단계에서 추가 필요.

**리스크**: 데이터 모델 문서 갱신이 계획에서 누락됨 — 사소하지만 다음 개발자 온보딩에 영향.

## 10. SQL/DB 최적화 (review-db)

**판정: 조건부 승인 — 사용자가 지적한 FK 남발 우려, 정량적으로 확인**

- 아키텍처 리뷰와 동일한 결론: `certification.catalog_id`는 FK보다 **인덱스만 있는 느슨한 연결**을 권장. 나머지 두 개(`subject`, `certification_question` → `catalog_id`)는 실제로 데이터 무결성이 깨지면 이번 버그가 재발하는 지점이므로 FK 유지가 맞음. 즉 "3개 다 FK"가 아니라 "2개 FK + 1개 인덱스"로 조정하면 사용자의 우려("FK 남발")를 줄이면서 핵심 안전장치는 유지 가능.
- 백필 쿼리의 매칭 기준(`TRIM(cert_name)` 이름 일치)에 대해 사전에 `SELECT DISTINCT TRIM(cert_name) FROM certification` 결과를 반드시 눈으로 검토하라는 계획의 "구현 전 확인 포인트"는 적절함 — 이게 안 되면 백필이 조용히 잘못된 매칭을 만들 수 있음.
- `certification_catalog.name`에 UNIQUE 제약을 거는 건 타당(동시 생성 방지의 근거이기도 함).
- 인덱스 계획에 명시가 없는 부분: `certification_question.catalog_id`, `subject.catalog_id`에 조회 패턴(WHERE catalog_id = ? AND subject_id = ?)에 맞는 복합 인덱스가 필요 — 기존 `idx_subject_cert`, 유사 인덱스처럼 새 컬럼 기준으로도 만들어야 함(리네이밍 시 기존 인덱스명도 함께 정리 권장).

**리스크**: FK 3개 전부를 강한 제약으로 가져가면 운영 부담 증가(위 아키텍처 리뷰와 동일 리스크). 인덱스 재생성 계획이 명시적으로 빠져 있음.

- 기존 프로젝트 컨벤션(Controller-Service-Mapper, `@Data` DTO, soft delete, Flyway 파일 컨벤션)을 그대로 따르는 계획 — 스타일 이질감 없음.

## 12. 백엔드 검증 (review-backend-verify)

**판정: 조건부 승인 — 구현 후 재검증 필수**

- 아직 코드가 작성되지 않은 계획 단계이므로 이 역할에서 실제 컴파일/기동 검증은 수행 불가 — **구현이 끝난 뒤 반드시 이 스킬(`review-backend-verify`)로 다시 검증받을 것**을 조건으로 조건부 승인.
- 계획에 있는 "로컬에서 직접 확인하기 전엔 완료로 보지 말 것"이라는 인계문은 이 역할의 존재 이유와 정확히 일치 — 이 원칙이 실제 구현 PR에서도 지켜지는지 확인 필요.

**리스크**: 계획 검토만으로는 실제 동작을 보장 못 함 — 구현 완료 후 별도 검증 라운드 필수.

## 종합 결론

**전체 판정: 조건부 승인 — 아래 3가지만 계획에 반영하면 구현 착수 가능**

1. **FK 설계 축소** (review-architecture, review-db 공통 지적, 사용자가 처음 제기한 우려와 일치): `certification.catalog_id`는 강한 FK 대신 인덱스만 있는 느슨한 연결로 완화. `subject.catalog_id`, `certification_question.catalog_id`는 FK 유지.
2. **catalogId가 null인 개인 기록의 화면 처리 결정** (review-fe): 문제풀이 버튼을 비활성화하거나 "문제은행 없음" 안내로 명시.
3. **이름 매칭 실패 케이스 검증** (review-test, review-incident): 백필 전 `SELECT DISTINCT TRIM(cert_name)` 결과를 실제로 확인하고, 공백/오타로 인한 매칭 실패 케이스를 최소 하나는 재현 테스트로 남길 것.

나머지 지적사항(문서 갱신, 커밋 단위 분리, 후속 IDOR 티켓 등)은 구현 단계에서 자연스럽게 반영 가능한 수준으로, 착수를 막을 사유는 아님.
