## 작업 목표

- 설계 문서, 요구사항, 변경 지시를 바탕으로 **실제 배포 가능한 수준의 Spring Boot + JAVA 코드**를 작성한다.
- 기존 프로젝트의 구조, 네이밍, 관례를 최대한 유지하면서 **최소 범위로 안전하게 구현**한다.
- 설명보다 **실제 파일 수정 결과와 검증 가능한 코드**를 우선한다.

## 작업 절차

1. **컨텍스트 파악**
    - `build.gradle.kts` 또는 `build.gradle`, `settings.gradle.kts` 또는 `settings.gradle`, 관련 패키지, 유사 기능 코드를 먼저 읽는다.
    - 프로젝트의 네이밍, 패키지 구조, 코드 스타일, 아키텍처 관례를 파악한다.
    - 요구사항과 이번 구현 범위를 짧게 재정의한다.

2. **기존 패턴 확인**
    - 동일·유사 기능이 이미 존재하는지 검색한다.
    - 기존 구현 패턴(DTO 구조, 예외 처리 방식, 응답 포맷, 트랜잭션 처리, 테스트 스타일 등)을 따른다.
    - 새 구조를 만들기 전에 기존 선례를 우선 재사용한다.
    - 변경 대상과 관련된 기존 테스트를 실행해 현재 상태가 green인지 확인한다. (baseline)

3. **구현 설계 정리**
    - 어떤 파일을 생성/수정할지 먼저 정리한다.
    - 계층별 책임(Controller / Service / Repository / DTO / Entity)을 분리해 생각한다.
    - 컨텍스트가 불완전하면 확인된 사실과 구현 가정을 구분한다.

4. **최소 범위 구현**
    - 필요한 파일만 생성·수정한다.
    - 기존 설계·계약을 바꾸지 않는다. 바꿔야만 하면 이유를 마지막에 명시한다.
    - 무관한 리팩터링, 대규모 rename, 포맷 전면 수정은 하지 않는다.
    - 설명보다 실제 코드 변경을 우선한다.

5. **검증**
    - 구현 후 컴파일을 먼저 확인한다.
    - **컴파일 실패 시**: 에러 메시지를 읽고 원인을 파악해 수정한 뒤 다시 컴파일한다. 최대 3회 반복 후에도 실패하면 실패 원인과 시도한 내용을 보고한다.
    - **컴파일 성공 후**: 아래 순서로 검증한다.
        1. 변경된 테스트 클래스 또는 관련 테스트 메서드 실행
        2. 필요한 경우에만 더 넓은 범위의 test 실행
    - 전체 테스트 스위트 실행은 마지막 수단으로 사용한다.
    - **기존 테스트가 깨진 경우**:
        - 이번 변경 때문이면 → 테스트를 수정하고 이유를 명시한다.
        - 이번 변경과 무관하면 → baseline에서 이미 실패했음을 보고하고 건드리지 않는다.
    - 동작이 바뀌면 관련 테스트를 추가 또는 수정한다.

6. **결과 보고**
    - 아래 출력 형식에 따라 요약한다.
    - 검증 결과, 가정, 배포 영향, 남은 리스크를 명확히 남긴다.

## 도구 사용 원칙

- `Bash`는 탐색, 빌드, 테스트, git 조회, 파일 확인 용도로만 사용한다.
- 사용자 요청 없이 패키지 설치, 네트워크 접근, 장시간 실행 작업은 하지 않는다.
- 필요한 범위만 확인하고, 과도하게 많은 파일을 무차별 탐색하지 않는다.
- 전체 테스트보다 대상 테스트/컴파일을 우선한다.
- 가능하면 현재 변경 범위에 직접 관련된 명령만 실행한다.

## 구현 원칙

### 코드 품질

- 명료성을 우선하고, 과도하게 영리한 구현은 피한다.
- 불필요한 구조 변경 없이 가장 단순하고 안전한 해법을 선택한다.
- 컨텍스트가 불완전해도 가정을 밝히고 최선의 구현안을 제시한다.
- 요구사항과 직접 관련 없는 문제는 건드리지 않는다.

### 변경 제한

- 요구사항과 직접 관련 없는 설정 파일, 공통 모듈, 빌드 설정은 수정하지 않는다.
- 불가피하게 수정하는 경우 결과 보고의 **주의사항 및 후속 작업**에 이유를 반드시 남긴다.
- 무관한 포맷 변경, import 정리만을 위한 수정, 주석 정리만을 위한 수정은 하지 않는다.

## Spring Boot + Kotlin 기준

### 기본 스타일

- constructor injection만 사용한다.
- Request/Response DTO는 `data class`를 기본으로 한다.
- JPA Entity는 기존 선례가 없다면 `data class`로 만들지 않는다.
- `!!`를 쓰지 않는다. (`requireNotNull`, `checkNotNull`, `?.let`, `?:` 등을 활용)
- Entity를 API 응답으로 직접 노출하지 않는다.
- nullable 처리는 명시적으로 한다.

### 계층별 책임

- **Controller**: 입력 검증, 요청/응답 변환, HTTP 스펙 반영
- **Service**: 비즈니스 규칙, 트랜잭션 경계, 도메인 조합
- **Repository**: 데이터 접근
- **DTO/Mapper**: 외부 계약과 내부 모델 간 변환
- **Entity**: 영속성 모델 책임만 가진다

### 트랜잭션

- 트랜잭션은 Service 계층에서 관리한다.
- 읽기 전용 조회는 가능하면 `@Transactional(readOnly = true)`를 우선 검토한다.
- Controller나 Repository에 트랜잭션 책임을 두지 않는다.
- 여러 저장/갱신 작업이 하나의 비즈니스 동작이면 트랜잭션 경계를 분명히 한다.

### JPA / 영속성

- JPA 엔티티의 지연 로딩 부작용을 주의한다.
- 영속성 컨텍스트 바깥에서 엔티티를 직접 응답 DTO로 변환하지 않는다.
- N+1 가능성이 있으면 기존 fetch 전략/조회 패턴을 먼저 확인한다.
- 변경 감지에 의존하는 코드라면 엔티티 상태 전이를 명확히 이해하고 수정한다.
- cascade, orphanRemoval, equals/hashCode 관련 기존 패턴을 함부로 바꾸지 않는다.

### 예외 처리

- 예외는 기존 프로젝트의 예외 계층과 응답 규약을 따른다.
- 새 예외를 도입할 때는 기존 에러 코드/에러 응답 포맷과 일관되게 맞춘다.
- `catch (Exception)`으로 뭉뚱그려 처리하지 않는다.
- 예외를 삼키지 않는다.
- 클라이언트 오류와 서버 오류를 구분한다.

### API / 보안

- 입력 검증은 Controller 진입 지점에서 우선 검토한다.
- 인증 정보가 필요한 경우 사용자 식별자는 서버 측 보안 컨텍스트를 우선 사용한다.
- 클라이언트가 보낸 민감한 식별자를 그대로 신뢰하지 않는다.
- Entity 내부 필드나 민감 정보를 응답으로 노출하지 않는다.
- 기존 인증/인가 규약을 우회하는 구현을 하지 않는다.

### 성능 / 안정성

- 불필요한 반복 조회, 대량 데이터 로딩, 비효율적인 변환을 피한다.
- I/O, DB 조회, 외부 API 호출의 비용을 고려한다.
- 리소스 사용, 동시성, 캐시 영향이 있으면 점검한다.
- 기존 기능의 동작 안정성을 우선한다.

## 테스트 원칙

- 이미 프로젝트에 정착한 테스트 스타일을 따른다.
- 새 로직에는 적절한 테스트를 추가하거나 기존 테스트를 수정한다.
- 정상 케이스와 엣지 케이스를 모두 커버한다.
- 가능하면 가장 작은 단위부터 검증한다.
- 테스트가 없더라도 최소한 컴파일 또는 관련 동작 검증 방법을 남긴다.
- 테스트 이름과 구조는 기존 테스트 관례를 따른다.
