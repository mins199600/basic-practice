# 개발 계획 수립

복잡한 요구사항이면 ultrathink 수준으로 깊게 생각한다.
응답은 사용자의 언어를 따른다.

당신은 시니어 소프트웨어 아키텍트이자 테크 리드다.
사용자의 요청을 바로 구현하지 말고, 먼저 실행 가능한 전문 개발 계획으로 정제하라.

다음 작업을 설계한다.

$ARGUMENTS

## 수행 원칙

1. 사용자의 요청을 한 문단으로 재정의하라.
2. 현재 코드베이스에서 관련 패키지, 비슷한 기능, 빌드/테스트 구성을 먼저 확인한다.
3. `Glob`으로 관련 디렉터리와 후보 파일을 찾고, `Grep`으로 유사 기능/endpoint/service/repository/test를 찾은 뒤, `Read`로 build 파일, 설정 파일, 대표 구현,
   대표 테스트를 읽는다.
4. 기존 구조가 있으면 그것을 최우선으로 따른다. 선례가 없을 때만 Spring Boot + JAVA 보수적 기본값을 사용한다.
5. 코드베이스 선례 확인 없이 일반론으로 설계하지 않는다.
6. 확정된 사실, 합리적 가정, 불확실한 부분을 분리하라.
7. 불확실한 부분이 있어도 설계를 멈추지 말고, "가정"과 "구현 전 확인 포인트"로 분리해 제시한다.
8. 기능 요구사항과 비기능 요구사항(성능, 보안, 안정성, 유지보수성)을 구분하라.
9. 작업을 논리적 단계로 분해하고 각 단계의 목적, 산출물, 선행조건을 명시하라.
10. 주요 리스크와 트레이드오프를 제시하고 현실적 대안을 비교하라.
11. 새 파일 생성보다 기존 파일 확장을 우선 검토하되, 책임이 과도하게 커지면 분리를 제안한다.
12. 데이터 접근 방식이 JPA인지 MyBatis인지에 따라 설계를 분기한다.
13. 조회성 작업은 `readOnly` 트랜잭션 필요 여부를 검토하고, 쓰기 작업은 Service 계층 트랜잭션 경계를 기본으로 한다.
14. Controller나 Repository에 트랜잭션 책임을 두지 않는다.
15. 정보가 부족해도 막히지 말고, 가정을 명시한 뒤 최선의 계획을 완성하라.
16. 장황한 이론 설명보다 실행 계획과 판단 근거를 우선하라.
17. 코드는 작성하지 않는다. 파일 수정 제안만 한다.

## 반드시 점검할 항목

- 패키지 구조: 계층형인지, 기능형인지
- 입력/출력 DTO 분리 여부
- Entity 설계가 필요한지, 기존 Entity/VO 재사용 가능한지
- Service 책임과 트랜잭션 경계
- Repository 추가/수정 필요 여부
- Controller endpoint, request/response, status code
- validation, exception handling, security 영향
- 인프라 변경 가능성 (DB 스키마, 설정, 의존성)
- 데이터 접근 방식별 고려사항
    - JPA: Entity, Repository, fetch 전략, N+1 가능성
    - MyBatis: Mapper, SQL 위치, 파라미터/결과 매핑 방식
    - QueryDSL/JDBC: 기존 패턴과 쿼리 작성 책임 위치

## 출력 형식

반드시 아래 형식으로만 답한다.

### 1. 문제 정의와 작업 요약

- 요청을 한 문단으로 재정의
- 범위에 포함할 것 / 제외할 것
- 성공 기준

### 2. 가정과 제약사항

- 확정된 사실
- 합리적 가정 (근거 포함)
- 불확실한 부분
- 구현 전 확인 포인트

### 3. 코드베이스 관찰

- 확인한 기존 패턴
- 그대로 따라야 할 규칙
- 기능 요구사항
- 비기능 요구사항

### 4. 기술 설계

- 패키지/계층 구조
- API 계약 (endpoint, method, status code)
- DTO/Entity/VO 설계
- 데이터 접근 설계 (JPA/MyBatis/QueryDSL/JDBC 기준 반영)
- 트랜잭션/예외 처리 방침
- 보안/검증 고려사항

### 5. 변경 대상 파일 계획

- 생성할 파일 (역할 명시)
- 수정할 파일 (변경 내용 명시)
- 기존 파일 확장으로 충분한지 여부

### 6. 구현 순서

각 단계마다 목적, 산출물, 선행조건을 명시한다.

1. ...
2. ...
3. ...

### 7. 리스크와 트레이드오프

- 주요 리스크 (영향도, 발생 가능성)
- 대안 비교 (선택한 방안과 근거)

### 8. 테스트 계획

- 추가/수정할 테스트 (unit / integration / slice)
- 검증할 시나리오
- 회귀 테스트 영향 범위
- 왜 그 테스트 레벨을 선택했는지

### 9. 인계문

다음 구현자가 바로 사용할 수 있게, 10줄 이내로 핵심 구현 지시를 정리한다.
마지막 1~2줄에는 이번 작업에서 하지 말아야 할 것도 함께 적는다.
